# Feature: Response Body Encryption

> Status: SDK + wire contract for SPA clients. Gateway Lua plugin is generated by pctl (orchestrator-owned: `tools/pctl/crypto.go`). Do not hand-edit generated Kong plugins.

One sentence: **gateway encrypts selected JSON responses with a per-token AES-256-GCM data key; the SPA decrypts transparently via `pfInstallFetch`.**

---

## 1. Threat model

This feature **raises the cost of casual interception** (shared Wi-Fi, misconfigured proxies, browser extensions that log response bodies). It is **not** a secrecy boundary against a determined attacker who already owns the device, the SPA process, or the session.

- Confidentiality of `PF_DATA_SECRET` and the derived per-token key matters.
- XSS that can read `sessionStorage` still obtains `dataKey`.
- Server-side logs and TLS termination remain the primary trust anchors.

Treat encryption as defense-in-depth for JSON APIs, not as a replacement for TLS, auth, or XSS hygiene.

## 2. Wire format

When a response is encrypted, the gateway sets `X-PF-Encrypted: 1` and replaces the JSON body with:

```json
{
  "v": 1,
  "alg": "A256GCM",
  "kid": "<tokenId or key id>",
  "iv": "<standard base64, 12 raw bytes>",
  "ct": "<standard base64, ciphertext || 16-byte GCM tag>"
}
```

- Algorithm: **AES-256-GCM**
- IV: **12 bytes**, random per response
- Tag: **16 bytes**, appended to ciphertext (WebCrypto `decrypt` expects `ciphertext||tag`, which is exactly `ct`)
- Encoding: **standard base64** (not URL-safe) for `iv`, `ct`, and the login `dataKey`

If `X-PF-Encrypted` is absent, the body is ordinary JSON.

## 3. Key derivation

- Shared secret: env **`PF_DATA_SECRET`** (auth and gateway only; never mounted into business services)
- Per-session data key: `HKDF-SHA256(PF_DATA_SECRET, salt=tokenId, info="pf-data", length=32)` → raw 32 bytes
- Login / token issuance response includes **`dataKey`** (base64 of those 32 bytes). The SPA stores it (typically `sessionStorage.setItem("pf_data_key", dataKey)`) and never handles ciphertext in app code.

Disable globally with **`PF_CRYPTO=off`** (gateway skips encryption; clients treat bodies as plaintext).

## 4. Service manifest

In `service.yaml`:

```yaml
crypto:
  encrypt_response: true   # gateway encrypts JSON responses for this service
  exempt:                  # path suffixes or exact routes that stay plaintext
    - /healthz
    /public/ping
```

Exempt routes are useful for health checks, public marketing JSON, and anything a non-SPA client must read without a data key.

## 5. Frontend SDK

| File | Role |
|---|---|
| [`sdk/js/pf-crypto-core.js`](../../sdk/js/pf-crypto-core.js) | Pure decode (`pfDecodeEncryptedBody`); no DOM |
| [`sdk/js/pf-crypto.js`](../../sdk/js/pf-crypto.js) | `pfDecryptResponse(response, dataKeyB64)` + `pfInstallFetch(getKey)` |
| [`sdk/js/pf-crypto.test.js`](../../sdk/js/pf-crypto.test.js) | Node round-trip + tamper test (`node --test`) |

After login:

```js
sessionStorage.setItem("pf_data_key", login.dataKey);
pfInstallFetch(() => sessionStorage.getItem("pf_data_key"));
// thereafter: const data = await (await fetch(url)).json(); // plaintext
```

`pfInstallFetch` wraps `window.fetch` so that encrypted responses still expose a `.json()` that returns the decrypted object. Unencrypted responses are unchanged.

## 6. Ownership boundary

- **This repo path (SDK + docs):** client decrypt helper and the public wire/config contract above.
- **pctl (`tools/pctl/crypto.go`):** generates the Kong/Lua encrypt plugin from manifests + `PF_DATA_SECRET` / `PF_CRYPTO`. Orchestrator-owned; do not edit by hand under `gateway/`.
- **Auth:** issues `dataKey` on login (and refresh, if configured) using the same HKDF inputs as the gateway.
